Complex typedefs on Windows again follow the C runtime
------------------------------------------------------
On Windows, ``npy_cfloat``, ``npy_cdouble`` and ``npy_clongdouble`` are again
typedef'd to the MSVC runtime's ``_Fcomplex``, ``_Dcomplex`` and ``_Lcomplex``
for *every* compiler targeting that runtime, including ``clang-cl`` and the
Intel LLVM compilers (``icx``, ``icx-cl``).

NumPy 2.4.5 made the Intel compilers use the C99 ``_Complex`` types instead.
That made ``#include <numpy/npy_math.h>`` fail to compile with those compilers,
since the accessors in that header call the runtime's ``creal()`` & co., which
are declared as taking ``_Dcomplex`` no matter which front end compiles them.

The two typedefs are layout-compatible, so extensions that only use these types
to describe array data were unaffected beyond the compile error. For extensions
that link ``npymath``, however, it also changed the signature of every function
there taking or returning a complex value by value - ``npymath`` is shipped as a
static library, built with MSVC for the official wheels. Which complex types are
available is a property of the C runtime, not of the compiler front end.

A new macro ``NPY_CPLX_IS_STRUCT`` is defined in ``npy_common.h`` whenever the
complex types are structs with a ``_Val[2]`` member - that is, on the C++ path
on all platforms, and on the MSVC runtime path. ``npy_math.h`` now branches on
it, so its accessors can no longer disagree with the typedefs.
